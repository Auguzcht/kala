# Backend handoff

Frontend pass findings that need a backend or product decision. Frontend changes keep the agreed API behavior and do not add client-side workarounds.

1. **“All unseen” test size:** section 7.2 of `docs/design/question-bank-design.md` lists “all unseen” as a supported set size, but `services/api/app/routers/practice.py` currently accepts only 5, 10, or 20 for bank sets. This frontend pass keeps the 5, 10, and 20 choices as directed. Decide whether the design text or backend validator should change in a later backend pass.
2. **Repeat banner after reopening a set:** `POST /practice/{course_id}/set` may return `includesRepeats`, but `GET /practice/{course_id}/sets/{set_id}` does not. The banner is therefore not reconstructible on retake. No frontend workaround is being added; decide whether saved-set responses should persist and return this metadata.
3. **Flashcard deck bank status semantics:** `GET /flashcards/{course_id}/deck` may return `bankStatus.usable` as true only when status is `ready` and `mcq_ready >= mcq_target` (`services/api/app/routers/flashcards.py:216-226`). `GET /courses/{course_id}/bank/status` uses the shared threshold `MIN_USABLE` and reports usable while a skill may still be building. The frontend uses the latter for state decisions. Consider aligning the optional deck field or removing it.
4. **Missing bank-state rows:** the bank status endpoint returns only `skill_bank_state` rows. An approved skill with no state row is absent from `skills`, and top-level `building` may be false even though the first set request would kick a build. The frontend treats an absent entry as `waiting_content` and waits for the shared endpoint’s `building` signal. Confirm that worker initialization reliably creates a row before this flow, or have the endpoint include approved skills without a state row and report them as waiting/building.
